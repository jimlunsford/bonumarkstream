# Bonumark Stream v0.8.0: ActivityPub Federation

Bonumark Stream can now remain your publishing home while also participating in the fediverse.

You still write, publish, organize, and preserve your work on your own site. ActivityPub adds an optional federation layer around that existing publishing system so people on Mastodon, GoToSocial, Misskey, and other compatible platforms can follow your Bonumark identity and receive your posts.

ActivityPub is disabled by default. Nothing federates until the site owner confirms the hosting requirements, creates a signing key, and enables the feature.

## Publish from your own site

Publishing remains a normal Bonumark action. When ActivityPub is enabled, Bonumark observes the completed local publication and queues the corresponding fediverse delivery afterward. A remote outage cannot prevent a post from being saved on your own site.

Federated publishing includes:

- new posts sent to followers;
- updates to already federated posts;
- deletes when a federated post is unpublished, trashed, or permanently removed;
- multiple images and image alt text;
- shared inbox delivery where compatible;
- asynchronous retries when a remote server is temporarily unavailable.

Bonumark has been tested directly with Mastodon, GoToSocial, and Misskey.io.

## Follow and participate without leaving Bonumark

The owner can follow a remote account by fediverse handle, profile URL, or actor URL. Follow and Unfollow relationships remain under owner control in Admin.

Accepted relationships feed the private frontend **Following** experience. Following is chronological, newest first, and non-algorithmic. It does not rank posts, recommend accounts, or create a public federated timeline.

From Following, the authenticated owner can:

- read sanitized remote posts;
- open a private conversation view;
- Reply with a normal Bonumark Stream Post;
- Like or Unlike;
- Boost or Unboost.

Following and its conversation views are private, excluded from public analytics and static export, marked `noindex`, and sent with `no-store` controls. Logged-out visitors and Commenter accounts cannot access them.

## Receive interactions from the fediverse

Bonumark accepts authenticated remote replies, Likes, boosts, and the matching Undo activities. Remote replies begin in moderation. Inbound Likes and boosts remain separate from Bonumark's anonymous local Like system, and remote actors never become local accounts.

The owner can block individual actors or entire domains. Blocks apply across follower relationships, Following, replies, interactions, cached remote content, and owner actions.

## Deleted posts stay deleted

A local Bonumark post and its federated object are related, but they are not the same identity.

The local post keeps its durable Bonumark ID through draft, publish, unpublish, trash, restore, and republish transitions. Each federated publication lifetime receives its own ActivityPub generation and object address.

Once Bonumark sends Delete for a generation, that object address is permanently retired and returns a Tombstone. Republishing the local post creates a new generation and a new fediverse object address. Old replies, Likes, boosts, and other interaction state do not move to the new generation.

This prevents a deleted fediverse object from silently becoming live again.

## Security and delivery reliability

Private signing keys are encrypted with installation-derived key material. Key creation and rotation perform a cryptographic self-test, and rotation does not change the actor identity.

Bonumark supports the established RSA HTTP Signature format used across the fediverse and RFC 9421 HTTP Message Signatures. Inbox requests receive digest, actor, key-owner, activity-identity, replay, and duplicate checks before they can change federation state.

Remote discovery and delivery use an HTTPS-only transport that rejects private, loopback, link-local, reserved, carrier-grade NAT, and metadata destinations. DNS, redirects, response size, request size, JSON depth, and network time are bounded.

Delivery runs asynchronously through server cron or protected web cron. The queue uses atomic claims, bounded batches, stale-processing recovery, exponential retry, `Retry-After`, dead-letter handling, immutable payload reuse, inspection, repair, safe retry, and permanent cancellation.

## Pause, suspend, or permanently retire federation

Bonumark keeps three operational actions separate:

- **Pause** temporarily takes the actor and inbox out of service and stops new federation work. Existing identity and relationships remain preserved.
- **Delivery suspension** keeps the actor and inbox active and continues recording local publication work, but does not claim outbound deliveries until suspension is lifted.
- **Permanent federation deactivation** sends Actor Delete and permanently retires the current actor URI.

Permanent federation deactivation cannot currently be reversed. The actor URI returns `410 Gone`, WebFinger stops advertising it, and Bonumark cannot re-enable or replace that identity. Pause or delivery suspension should be used whenever the owner may want federation again.

## Hosting requirements

ActivityPub requires:

- a canonical root-level HTTPS site URL;
- domain-root `/.well-known/webfinger` routing;
- PHP OpenSSL;
- PHP cURL with outbound HTTPS access;
- a high-entropy installation security salt;
- protected private Bonumark paths;
- writable runtime storage;
- dependable server cron or protected web cron;
- reverse-proxy forwarding for the documented signature, digest, host, content-type, and content-length headers.

A subdirectory installation cannot provide standards-compliant domain-root WebFinger automatically. It needs explicit hosting-level routing before Bonumark will allow ActivityPub to be enabled.

## Upgrade and database changes

v0.8.0 adds migrations `0018` through `0028`. They create the ActivityPub identity, key, publication, delivery, follower, Following, interaction, blocking, actor-retirement, and remote-actor lifecycle records required by federation.

ActivityPub remains disabled after a normal upgrade until the owner enables it. The migrations do not rewrite existing post bodies or replace existing posts, profiles, media, comments, Likes, themes, imports, exports, runtime state, or other owner data.

Back up the database and site files before upgrading. The maintained automatic and owner-run upgrade line continues to begin at v0.4.0.

## Known limitations

- Misskey.io accepted Bonumark Update activities during interoperability testing but did not apply changed Note text. No Bonumark payload defect was identified.
- Sharkey.world connection failures observed during testing appeared server or connection specific.
- NodeInfo is not implemented.
- Automatic domain migration is not implemented.
- Replacement actor identities after permanent retirement are not implemented.
- Multi-user federation is not implemented.
- Public federated timelines are not implemented.
- Followers-only or private federation is not implemented.
- Direct messages are not implemented.

For setup, operating states, troubleshooting, and the full security and lifecycle contract, see [ActivityPub in Bonumark Stream](../ACTIVITYPUB.md).
