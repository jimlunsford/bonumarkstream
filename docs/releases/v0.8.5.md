# Bonumark Stream v0.8.5: Admin Black-and-White Palette Development Build

**Unreleased development build. Not a public release or deployment approval.** Public v0.8.3 remains the current public release.

v0.8.5 supersedes the v0.8.4 development build, which was not accepted because its Admin palette read as greenish black. It is built on the v0.8.4 development staging source (`b902594272c7c367f1ff795d00b7174662eef980`) and changes only Admin color, the tokens that carry it, version identity, documentation, and the release manifest. It adds the repository `CLAUDE.md` contributor instructions.

## Palette

The dark Admin tokens in `assets/admin-shell.css` are:

| Token | Value |
|---|---|
| `--admin-bg`, `--admin-surface-3` | `#000000` |
| `--admin-surface`, `--admin-surface-2`, `--admin-sidebar` | `#0d0d0d` |
| `--admin-surface-raised`, `--admin-sidebar-hover`, `--admin-selected` | `#1f1f1f` |
| `--admin-warning-surface` | `#171717` |
| `--admin-text`, `--admin-sidebar-text` | `#ffffff` |
| `--admin-muted`, `--admin-subtle` | `#a3a3a3` |
| `--admin-border` | `#262626` |
| `--admin-border-strong`, `--admin-control-outline` | `#737373` |
| `--admin-accent` / `--admin-accent-dark` / `--admin-accent-text` | `#ffffff` / `#d4d4d4` / `#000000` |
| `--admin-success` / `--admin-danger` / `--admin-warning` | `#4ade80` / `#f87171` / `#facc15` |
| `--admin-overlay` (new) | `rgba(0, 0, 0, 0.7)` |
| `--admin-shadow-color` (new) | `rgba(0, 0, 0, 0.4)` |

Primary buttons are white with black text. Success, danger, and warning are the only hues; status-tinted backgrounds are neutral surfaces with status-colored text or borders. In-content text links and link-style buttons are underlined so they remain distinguishable from white body text. Focus rings are white on black.

## Included changes

- Replaces the dark token values. The dormant `admin-appearance-light` palette is unchanged.
- Routes every hardcoded color observed rendering on an Admin screen, including forced hover, focus, and active states and the empty, warning, error, and destructive states, through the tokens. Legacy `admin.css` rules that do not render on any audited Admin screen are left unchanged.
- Unscoped legacy `admin.css` rules that can also match the installer or the public-theme preview use the token with the previous literal as the `var()` fallback, so those non-Admin pages render as before.
- The sign-in screen and the Admin preview bar share the color tokens through `body.bonumark-admin-login` and `.bonumark-preview-bar`; neither receives shell layout or typography.
- No layout, spacing, typography, or behavior changes. Public themes, the bundled Midnight Ledger theme, and public-site CSS are unchanged.

## Upgrade and migration impact

Adds no database migration. The migration set remains 0001 through 0028 and is unchanged from v0.8.4. A target already through 0028 has no pending migration, subject to inspection of its actual ledger and migration hashes.

Use the installation's existing supported Admin ZIP or owner-run upgrade workflow, including from an installed v0.8.4 development build. The canonical ZIP is `bonumark-stream-v0.8.5.zip`, containing the single root `bonumark-stream-v0.8.5/` and a final release manifest. Core asset URLs carry the version and a content fingerprint, and the service-worker cache name changes to `bonumark-stream-static-v0.8.5`, so browsers fetch the new stylesheets.

Preserve configuration, installed.lock, content, accounts, settings, API and federation state, media, custom themes, and runtime storage. Before deployment, verify a full files-and-database recovery point and rehearse the exact ZIP against an isolated copy of the target installation.

## Reproducible package

From the finalized source commit, use the canonical repository packaging mechanism:

```sh
git archive --format=zip --prefix=bonumark-stream-v0.8.5/ HEAD -o bonumark-stream-v0.8.5.zip
sha256sum bonumark-stream-v0.8.5.zip
```

Generate the release manifest after all package contents are final and before committing. Do not change packaged files after manifest generation. Validate the extracted ZIP with the strict package smoke test, PHP/JavaScript/JSON checks, complete manifest coverage, and the database and recovery regressions. A built ZIP keeps its version number; any later change ships as a new version.
